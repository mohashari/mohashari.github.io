In modern bare-metal deployments, bootstrapping host identity without cloud-native metadata services is a notoriously fragile problem. Unlike virtual machines running in AWS or GCP that leverage integrated IAM instance profiles to obtain temporary credentials, a physical server booting in a private cabinet must somehow prove its identity before it can pull database credentials, TLS certificates, and API keys from HashiCorp Vault. The standard industry anti-pattern relies on baking static AppRole `RoleIDs` and `SecretIDs` into disk images or injecting them via configuration management tools like Ansible or SaltStack. If an NVMe drive is decommissioned without proper cryptographic erasure, or if an attacker compromises a backup of the configuration database, those static secrets grant long-term access to your entire secret store. To eliminate this vector, we must leverage the Trusted Platform Module (TPM) 2.0 chip physically soldered to the motherboard. By validating the server's identity and measured boot state at the hardware layer, we can automatically mint ephemeral Vault tokens that exist only in host memory (`tmpfs`) and expire within minutes if the hardware is tampered with or rebooted.

## The Core Problem: The Bootstrapping Vulnerability

When provisioning secrets in a bare-metal datacenter, you face a classic chicken-and-egg dilemma. To fetch secrets from HashiCorp Vault, an application needs a token. To get a token, the application must authenticate. To authenticate, it needs a secret (such as a private key or an AppRole SecretID). If this initial credential is saved on the server's persistent storage, the entire platform's security is only as strong as the physical security of the disk drives.

Physical security failure modes are more common than many infrastructure teams care to admit:
1. **Improper Disk Decommissioning**: Failed enterprise NVMe drives are often replaced by vendors. If the drive is not thoroughly shredded or cryptographically erased before being handed over, raw sectors containing configuration files or static tokens can be recovered.
2. **Cold Boot Attacks**: A malicious actor with physical access to the server cabinet can perform a hard reboot and dump the contents of the RAM, extracting long-lived tokens.
3. **Hypervisor or Host Compromise**: If an attacker gains root access to the host operating system, any secret residing in persistent files is permanently compromised.

We need a mechanism where the host identity is tied to physical hardware, cryptographically verified by a third-party root of trust (the TPM manufacturer), and validated against the boot configuration of the server. The token should never be written to non-volatile storage, residing only in a volatile memory partition (`tmpfs`), and should automatically expire when the server is powered down or rebooted.

## TPM 2.0 Cryptographic Primitives: EK, AK, and PCRs

To implement a hardware-rooted identity, we must understand the core components of the TPM 2.0 architecture:

### 1. The Endorsement Key (EK)
The Endorsement Key is a unique, persistent cryptographic key pair (typically RSA 2048-bit or ECC NIST P-256) burned into the TPM's non-volatile memory by the silicon manufacturer (e.g., Intel, AMD, Infineon, STMicroelectronics) during fabrication. The private component of the EK never leaves the TPM. The public component is published in an **EK Certificate** signed by the manufacturer's root Certificate Authority (CA). This certificate provides cryptographic proof that the EK belongs to a genuine physical TPM compliant with TCG (Trusted Computing Group) standards.

### 2. The Attestation Key (AK)
While the EK proves the TPM is genuine, it cannot be used directly to sign user data or system states to prevent tracking the system's identity across the internet. Instead, we generate an ephemeral **Attestation Key (AK)**. The AK is a restricted signing key that is bound to the EK. The TPM uses the AK to sign platform measurements, proving that those measurements were generated by a genuine hardware module.

### 3. Platform Configuration Registers (PCRs)
PCRs are 256-bit registers inside the TPM that store cryptographic measurements of the boot environment. PCRs cannot be set directly; they can only be **extended** using a one-way hashing function:

$$\text{PCR}_{\text{new}} = \text{SHA256}(\text{PCR}_{\text{old}} \mathbin{\Vert} \text{Value})$$

This design makes it mathematically impossible to fake a boot state. If any file, configuration, or firmware component in the boot path is modified, the resulting PCR values will diverge from the expected "golden state." In a secure bare-metal architecture, we measure:
* **PCR 0**: SRTM, BIOS, and motherboard firmware.
* **PCR 2**: Option ROMs (PCIe device firmware, raid controllers).
* **PCR 4**: The bootloader image (e.g., GRUB/shim).
* **PCR 7**: Secure Boot configuration, including active database (db) keys and the shim authority.

## The Credential Activation Protocol

To prove that the host possesses a genuine TPM and that the Attestation Key is resident within that specific TPM, we use a two-step challenge-response protocol known as **Credential Activation** (`MakeCredential` and `ActivateCredential`).

1. **Host Request**: The host agent reads the EK Certificate and generates a new AK. It sends the EK Certificate, the AK Public Key, and a signed PCR Quote to an external **Attestation Verifier**.
2. **Verifier Challenge (`MakeCredential`)**: 
   * The verifier validates the EK Certificate chain against the manufacturer's root CA.
   * It checks that the signed PCR values match the known golden boot state of that specific server.
   * It generates a random 32-byte secret (the challenge).
   * It encrypts this secret using the EK Public Key, binding it cryptographically to the name (hash of the public key structure) of the AK. This encrypted package is called the credential blob.
3. **Host Response (`ActivateCredential`)**:
   * The host receives the credential blob.
   * The host passes the blob to its TPM via the `ActivateCredential` command, pointing to both the EK and AK handles.
   * The TPM verifies that the AK name matches the one specified in the challenge.
   * Inside the hardware shield of the TPM, it decrypts the secret using the EK Private Key.
   * The TPM returns the raw 32-byte secret to the host agent.
   * The host agent returns this secret to the verifier, proving it has physical control over the certified TPM.
4. **Token Issuance**: The verifier validates the returned secret and exchanges it for a short-lived, role-bound HashiCorp Vault token, which it sends back to the host agent.

## Production Hardening: Real-world Failure Modes

While this architecture eliminates static bootstrap credentials, running it in high-scale production exposes several real-world operational challenges that you must design around.

### 1. PCR Drift and Kernel Updates
The most common operational failure occurs during standard patch management. When your host OS gets a kernel update, a GRUB configuration change, or a BIOS update, the cryptographic hashes for PCR 0, 2, 4, and 7 change. When the machine next boots, the attestation quote will not match the verifier's catalog of "golden states."
* **Impact**: The node fails boot attestation, cannot retrieve its Vault token, and the application fails to start.
* **Mitigation**: Implement a CI/CD integration with your package manager (e.g., `apt` or `dnf`). When an kernel update is built, run a dry-run tool like `tpm2-predict` to compute the expected hashes of the new kernel/initramfs, and register these new values to the verifier's database *before* issuing a reboot command to the node.

### 2. TPM Dictionary Attack Lockouts
TPM 2.0 devices have built-in defenses against brute-force attacks. If the local host agent attempts to execute commands using invalid authorization values or corrupted contexts, the TPM will trigger a self-defense lockout.
* **Impact**: The TPM refuses to perform cryptographic operations (including `ActivateCredential`), blocking all attestation requests for hours.
* **Mitigation**: Implement a strict cooldown and back-off policy in the host bootloader script. If an attestation attempt fails, do not retry in a rapid loop. The agent must log the error, enter a back-off state, and alert the infrastructure team. Additionally, make sure to explicitly configure the TPM Lockout parameters (`tpm2_dictionarylockout`) during initial OS installation to establish a clean timeout value.

### 3. High Availability of the Verifier
Because bare-metal hosts depend on the verification service to fetch their identity credentials at startup, the Attestation Verifier becomes a critical single point of failure.
* **Impact**: If the verifier service goes offline, newly spun-up hosts or hosts recovering from a reboot cannot mount their secrets.
* **Mitigation**: Deploy the verifier as a stateless, multi-node service behind a highly-available load balancer. Since the verifier does not hold any host state (it only checks incoming EK signatures against static vendor root CAs and PCRs against a database), it can scale horizontally. Maintain the "golden configurations" in an encrypted, distributed database with replication across multiple failure domains.
